# 代码审查记录（2026-07-26）

> 审查人：Claude（主审）+ 独立 Reviewer 子代理（交叉验证）
> 范围：`src/`、`web/app`、`data/`、配置文件全量走查
> 结论：架构选型合理（单体 + JSON 状态，匹配当前 1 人 / 2 任务的实际规模，未过度设计 `FEASIBILITY_REPORT.md` 里的 NestJS/Postgres/Redis 重架构），但存在若干会导致**提醒静默丢失**或**监控静默失效**的真实缺陷，记录如下，尚未修复。

## 🔴 高优先级

### 1. 通知发送失败也会被标记为"已发送"
- **位置：** `src/notifiers/telegram.ts:39-63`、`src/service.ts:60-61`
- **问题：** `sendAlert` 内部把所有异常都吞掉，从不返回成功/失败状态；`service.ts` 不管发送成不成功都紧接着调用 `dataManager.markAsSent(item)`。
- **后果：** Telegram 一次网络抖动 / 限流 / token 失效，这条捡漏商品就永久标记为已发，不会重试，且没有持久化日志可事后排查（`winston` 已装但代码里从未使用，只有 `console.log`）。
- **修法：** `sendAlert` 返回布尔值（或抛错），`service.ts` 只在确认发送成功后才 `markAsSent`。

### 2. Web 仪表盘与 service.ts 抢同一份 `tasks.json`，无锁无原子写
- **位置：** `web/app/api/tasks/route.ts`、`create|update|delete/route.ts`、`src/data-manager.ts:24-32`
- **问题：** 一开始误判 `web/` 是空模板——实际上 `web/app/page.tsx` 是真实页面（6.2KB），且有完整的 `/api/tasks/{list,create,update,delete}` CRUD 接口，各自独立"整读整写" `data/tasks.json`，不走 `data-manager.ts`，没有原子写（无 temp 文件 + rename）、没有校验、没有锁。
- **后果：** 两个请求并发（如两个浏览器标签同时改任务）会发生经典的"后写覆盖前写"；若写到一半崩溃，`tasks.json` 变成非法 JSON，`DataManager.getTasks()` 捕获解析错误后返回 `[]`——**整个监控服务此后每轮任务数为 0，`🏁 Cycle Complete` 仍正常打印，但实际什么都没在监控**，没有任何报错提示。
- **修法：** 所有任务写操作统一走一个校验 + 原子写（temp 文件 + rename，必要时加简单写队列）的 `DataManager` 方法。

## 🟠 中优先级

### 3. `/api/tasks/*` 无任何鉴权
- **位置：** `web/app/api/tasks/*/route.ts`
- 任何能访问到该 Next.js 端口的人都可增删改监控任务，叠加第 2 点的并发问题风险更大。`web/README.md` 仍是默认建议直接部署 Vercel 的说明，当前无任何机制阻止其被暴露到公网。
- **修法：** 部署到本机以外前，先在 `middleware.ts` 加共享密钥 / Basic Auth 校验。

### 4. `minPrice` 的 `||` 误判 0 为"未设置"
- **位置：** `src/service.ts:32`：`const minPrice = task.minPrice || (task.priceThreshold - 15000);`
- 仪表盘"最低价"留空时前端 `Number('')` 算出 `0`，`0 || x` 会走 fallback，把"不设下限"悄悄变成"下限 = 阈值-15000"——恰好过滤掉这个捡漏机器人最该抓的、最便宜的那批漏单。
- **修法：** 改成 `task.minPrice ?? (task.priceThreshold - 15000)`。

### 5. "日本时间 8-24 点"用的是服务器本地时区
- **位置：** `src/service.ts:14-18`（`now.getHours()`）
- 现在能跑对纯属本机时区凑巧接近 JST，一旦换到云端 UTC 服务器部署，监控窗口会整体偏移且不报错。
- **修法：** 显式取 `Asia/Tokyo` 时区小时数，例如 `Intl.DateTimeFormat` 指定 `timeZone: 'Asia/Tokyo'`。

### 6. `sent_items.json` 非原子写
- **位置：** `src/data-manager.ts:52-58`（`markAsSent`）、`:85`（`cleanupOldData`）
- 写到一半崩溃 → 文件损坏 → 下次解析失败被 catch 成 `{}` → 去重历史全部清空 → 所有历史商品在下一轮被当"新品"重新推送一遍。
- **修法：** 同样改为 temp 文件 + `fs.rename` 的原子写。

### 7. 浏览器崩溃不会自愈
- **位置：** `src/scrapers/paypay.ts:15`（`if (!this.browser) await this.init();`）
- Chromium 意外断开时 `this.browser` 从不被置空，单例被所有任务共用，一次崩溃 = 所有任务永久停止抓取，直到手动重启进程。
- **修法：** `init()` 中监听 `this.browser.on('disconnected', () => { this.browser = null; })`。

### 8. 零反爬措施
- **位置：** `src/config.ts:13`（`proxy` 字段）、`src/scrapers/paypay.ts:7-11`
- `PROXY_URL` 读了但全项目 grep 确认从未被引用，`chromium.launch()` 无代理、无 stealth 插件。自家 `FEASIBILITY_REPORT.md` 明确写了"高频抓取必须用住宅代理"，代码未落实，5 分钟固定频率长期跑有被封 IP 的风险。
- **修法：** 把 `config.proxy` 接入 `chromium.launch({ proxy: { server: config.proxy } })`，或先删掉这个没用的配置项。

### 9. 选择器脆弱，零结果无告警
- **位置：** `src/scrapers/paypay.ts:33,48-56`
- 价格靠正则扒 `textContent` 里的"円"字样，标题靠 `img.alt`，无站点特定 class。PayPay 一改版即失效，`scrape()` 直接返回 `[]`，与"当前真没上新品"表现完全一致，不会报警。
- **修法：** 在 `DataManager` 里记录连续零结果轮数，超过阈值（如连续 12 轮≈1小时）主动发一条 Telegram 警告。

### 10. 首次 `runCycle()` 调用未包 try/catch
- **位置：** `src/service.ts:92-93`
- 后续每轮定时调用都有 `.catch(console.error)`，唯独启动时那一次没有；若第一轮抛出同步异常会让整个 Node 进程崩溃，且无 pm2/systemd 等进程守护自动重启。
- **修法：** 改成 `await runCycle().catch(console.error);`，并补一个进程守护配置。

## 🟡 低优先级（不影响功能，可顺手清理）

11. **`.env` 明文 token 落在 Google Drive 同步目录**——虽 `.gitignore` 挡住未进 git，但明文 token 会持续同步到 Google 服务器。建议把 `.env` 移出同步目录或加同步排除名单，并考虑轮换该 token。
12. **`winston` 装了未用**——`package.json` 中的死依赖，日志全靠 `console.log`，进程崩溃后无持久化日志可查。
13. **魔法数字散落各处**——5 分钟轮询、5s/2s 延迟、`priceThreshold - 15000` 兜底差值等，未收进 `config.ts`，调参需改代码重新部署。
14. **`web/app/api/tasks` 存在未使用的重复端点**——根路径 `route.ts` 的完整 CRUD、`update/route.ts` 里重复的 `DELETE` handler，前端实际只用 `list/create/update/delete` 四个端点，其余是死代码。

## 如果只修 3 件事
1. **`sendAlert` 加返回值，`service.ts` 只在确认发送成功后才 `markAsSent`**（问题 1）——当前唯一会真实"丢提醒"的高确定性 bug。
2. **给 `web/app/api/tasks/*` 加鉴权，写操作统一走原子写的 `DataManager` 方法**（问题 2、3）——避免仪表盘并发写坏 `tasks.json` 把整个监控服务默默拖死。
3. **`service.ts:32` 的 `||` 改成 `??`**（问题 4）——一行改动，直接关系到这个机器人的核心目的：抓最便宜的漏单，现在反而在过滤掉它们。
